# 平井：D/E分割を X/Y に改名 ＋ 実在の隣接2筆(1170-1・1404-4)を新D/E区画として追加

## 背景（腱さんの発言の要約）
今日役場で公図・土地の管理台帳を確認し、新事実が判明した。現在ABCで3分割している敷地(1170-4)の隣に、
同じ所有者の隣接2筆がある：**1170-1(466㎡)**、**1404-4(251㎡)**（さらに北の1404-4）。これらも売買候補
（部分売却／全部売却の両案があり得る）なので高低差も評価したい。

- 既存の「D/E分割」（ABC敷地を任意%で2分割する機能。今まで呼んでいた D区画/E区画）は **X区画/Y区画** に改名する。
  **X＝北側（腱さんが買いたい方）、Y＝残る方**。E区画が主役だった仕様はそのまま「Xが主役」に読み替える
  （中身のロジックは変えない。E→X、D→Yの単純な呼び替え）。
- 空いた「D/E」という名前を、今度は**実在の隣接2筆**に使う：**D区画＝1170-1、E区画＝1404-4**。
  これは%で動かせる分割ではなく、固定された実在の筆界（新しいsubAreaSetsの案）。

## 新区画の座標（このセッションで測量・検証済み。以下を「正」として使うこと）
公図(`_input/Hirai1298/平井1170-4公図.pdf`)から、以下の手順で座標を求めた：
1. PDFをA3(841×1190pt)・400dpiでラスタ化。
2. 図面右上のグリッド十字（平面直角座標系第VIII系、X=-100650, Y=43000）のピクセル位置を実測。
3. 1:500スケール・A3用紙サイズから **0.03175 m/px** を算出（グリッド十字はこの検算にも使った）。
4. 北を上とする回転なしの相似変換（グリッド十字を原点、上記スケール）でピクセル→平面直角座標(X,Y)に変換。
5. **検証**：build_hirai.pyの既知点(K50, K45, K47, K53, R212)を同じ変換でピクセル位置に逆投影し、
   公図上の実際の境界線に一致することを確認した（視覚検証、大きなズレなし）。この変換自体の信頼度は高い。
6. 1404-4・1170-1の境界を公図のピンク蛍光ペン強調線＋黒い境界点ドットからトレースし、同じ変換で
   平面直角座標(X,Y)→lat/lon(Tokyo/Bessel→JGD、build_hirai.pyと同じ3パラメータ変換)→
   `SITE_XFORM`によるshape空間座標、まで変換した。

**shape空間の座標（そのまま`pts`に使える）**:
```js
// D区画＝1170-1（トレース面積 約303㎡。登記面積466㎡との差 -35%。要注意、後述）
D_1170_1 = [[-10.3,46.05],[9.98,31.68],[14.68,27.58],[15.67,27.64],[15.57,26.75],[31.02,26.93],[30.77,27.47],[26.24,28.51],[15.64,35.42],[12.0,47.78]]
// E区画＝1404-4（トレース面積 約310㎡。登記面積251㎡との差 +23%）
E_1404_4 = [[10.23,72.75],[16.23,66.16],[14.19,63.49],[11.11,57.14],[10.33,52.49],[12.0,47.78],[-10.3,46.05],[-3.84,54.18]]
```

**⚠️ 精度についての重大な注意（実装時にコード中へ必ずコメントとして残すこと）**：
- 座標変換の仕組み自体（ピクセル→実座標）は検証済みで信頼できる。
- しかし公図は**手書き注記・蛍光ペンの太さがある簡易図**で、正式な座標求積表（1170-4/1170-5にあるような
  Xn,Yn付きの地積測量図）ではない。1170-1は特に、トレースした形状の面積が登記面積(466㎡)と**35%**も
  ズレており（複数の境界解釈を試したが466㎡に届く形状を確信を持って再現できなかった）、**形状・位置とも
  参考程度**。1404-4は+23%で1170-1よりは近いが、これも同様に「参考」の精度。
- **正式な地積測量図（座標求積表付き）が1170-1・1404-4について別途手に入れば、その時に差し替えるべき**。
  それまでは「大まかな位置関係・おおよその高低差傾向」を見るための暫定形状として扱う。

## やること
### 1. 既存の%分割機能をDE→XYへ改名（中身は不変）
- `SITE.subAreaSets`のキー名を `'DE'` → `'XY'` に変更（`subAreaSets:{'ABC':[...], 'XY':[...], 'DE':[...]}` の3案構成にする）。
- `applyDeSplitPercent()`内の `SITE.subAreaSets.DE=[{no:'E区画',...},{no:'D区画',...}]` を
  `SITE.subAreaSets.XY=[{no:'X区画',...},{no:'Y区画',...}]` に変更（E→X、D→Yの単純置換。並び順=Xが先頭のまま）。
- 変数名・関数名は無理に全部XYへ変えなくてよい（`applyDeSplitPercent`等の関数名はそのままでも動作に支障なし。
  ただし文言・UI表示（「E区画」「D区画」という日本語ラベル・ヒント文・進捗メッセージ）は全て「X区画」「Y区画」に変える）。
- `#deSplitPanel`まわりのHTML文言（「D/E分割ライン」「E区画が主役」「E区画の割合」「E区画 目標面積」等）を
  「X/Y分割ライン」「X区画が主役」「X区画の割合」「X区画 目標面積」等に変更。
- `#deSplitPanel`の表示条件（現在 `subAreaVariant==='DE'` でパネルを出す）を `subAreaVariant==='XY'` に変更。
- 区画別の内訳見出しの文言はそのまま`${subAreaVariant}`を表示しているだけなので変更不要（自動でXY/DE/ABCが出る）。

### 2. 新しい「実在のD/E」を追加
- `SITE.subAreaSets.DE = [{no:'D区画 1170-1', pts: D_1170_1}, {no:'E区画 1404-4', pts: E_1404_4}]`
  を追加（上記の座標をそのまま使う。%で動的に変わるXYと違い、DEは固定形状＝`applyDeSplitPercent()`のような
  動的再生成は不要）。
- `toggleSubAreaVariant()`は既に`Object.keys(SITE.subAreaSets)`で循環する作りなので、キーが3つ
  (`ABC`,`XY`,`DE`)になれば自動的に3案循環になるはず（要動作確認）。循環順は
  `ABC→XY→DE→ABC`で問題ない（オブジェクトのキー定義順に依存するので、定義順もこの順にする）。
- `updateSubAreaToggleUI()`内、`#deSplitPanel`の表示条件は`XY`の時だけ（上記1で対応済みならOK）。
  新しい`DE`（実在筆）の時は`#deSplitPanel`を出さない（%スライダーは使えない固定形状のため、`display:none`のまま）。
- `priceSimGroups()`（967行付近）は現状 `if(subAreaVariant==='DE' && ...) groups.push({label:'DE', items: SITE.subAreaSets.DE})`
  という「XY表示中でもDEデータを追加するかどうか」の分岐だった（旧仕様：ABC表示中でも%分割DEは出さない、
  XY表示中にABCへ追加でDE(旧E/D)を足す、という設計だった）。今回、DEの意味が変わった（%分割ではなく実在筆）ため、
  設計を見直す：**ABC表示中は常にABCのみ／XY表示中はXYのみ／DE表示中はDEのみ**、を基本とし、価格シミュレーションは
  「今表示中の案のグループ＋常にABCも比較対象に含める」かは実装者の判断でよいが、**最低限、表示中の案自体が
  必ず出ること**を優先する（現状のロジックのまま`subAreaVariant`をキーにgroupsを作れば自然にそうなるはず）。
- 価格シミュレーションの基準区画`priceSimBaseRegion()`は`SITE.subAreaSets.ABC`からA区画を探す実装のまま
  で問題ない（基準はA区画のまま変更なし）。
