# D/E（1170-1・1404-4）を実座標でベクトル化する（4回目・新方式）

## 背景・経緯（必ず先に読むこと）

`docs/BUGLOG.md` と `index.html` の `SITES.hirai.subAreaSets` コメント参照。D/Eのベクトル化は
過去3回失敗して2026-08-19に撤退・封印されている（公図の手描きピンク線から座標を機械抽出しようとして
形状を破綻させた／登記面積へ合わせる補正を重ねて作文した／モルフォロジー処理が細長い帯を分断した）。

腱さんが今回、**まったく別の方法**を明示的に指示した：

> みどりE　赤D　でざつだけど指定した／このとおりに　つぎはベクトル化して／背景の道路とかわは見えてる？
> 今回の色塗りはめやすでかなり雑なセンなのでそのままつかわないで／道路と川とC区画のへりに囲まれたかたちで
> DとEを描画する　そのうえでDとEの面積（ABCと相対的にただしいすうち）を算出表示する／
> 最終的にDとEの境界線を上下に任意に動かすことで正しい面積に調整する

つまり：
1. 腱さんが `_input/Hirai1298/補正.png` でざっくり緑=E・赤=Dと塗った領域は**目安**（そのまま使わない）。
2. Dの外周・Eの外周は、**公図のピンク線ではなく実在の道路・川・C区画（ABCの敷地境界）の辺**で囲まれた
   形にする。
3. 面積を算出・表示する。
4. **DとEの境界線を腱さんが上下に動かして面積を調整できるUIを付ける**（本質は「正確な座標は無いので
   実測できる範囲＝道路・川・敷地境界だけを機械的な正とし、残りは腱さんが目で見て調整する」という、
   既存の`kouzuAdj`（公図オーバーレイの手動位置合わせ）と同じ設計思想）。

今回は「公図の手描き線をどう解釈するか」という不確実な作業を避け、**地図タイル上に実在する道路・川を
Leafletの`map.mouseEventToContainerPoint`→`containerPointToLatLng`で直接クリック採取し、既存の
`SITE_XFORM`の逆変換でABCと同じローカル座標系に変換した**（後述の座標データは全てこの方法で取得済み・
検算済み）。**この座標データを疑わず、そのまま使うこと。** 再度公図画像からの推測トレースに戻らないこと。

## 幾何モデル

ABC敷地（`SITES.hirai.shape`）のうち、D/Eと接する辺は「B/C角」→「東端角」→「山頂(北端)」の3点を
通る折れ線（下記`abcEdge`）。**この折れ線から先、山頂を頂点として2つの独立した“くさび形”がD・Eとして
外側に張り出す**という構造だと判明した（腱さんの雑な色塗りでも山頂を挟んで緑=E・赤=Dに分かれていたのと
整合する）。

- E＝山頂から**道路**沿いに外側へ張り出すくさび（北西側）
- D＝山頂から**川**沿いに外側へ張り出すくさび（南東側）、南端は「B/C角」でABC辺と合流

道路・川はどちらも山頂の近くを通っており、遠くまで辿ると全然関係ない山中の道路・川まで拾ってしまい
面積が登記(D466㎡/E251㎡)の3〜6倍に膨らむことを検算で確認済み（下記「採用したポイント」は既にこれを
踏まえて**山頂に近い区間だけ**に絞ってある）。

### 採用する座標（ローカル座標系＝`SITES.hirai.shape`と同じx=東/y=北のメートル単位。すべて検証済み）

```js
const tip = [-7.63, 49.53];   // 山頂（ABC辺上。D・Eの共通の起点）
const bc  = [16.49, 0.79];    // B/C角（ABC辺上。Dが合流する側）

// 道路沿い（山頂に近い順）。Eのくさびはこの中から何点採用するかを腱さんが調整する。
const roadPts = [
  [10.94, 75.96],   // 山頂から最短距離(約21m)
  [0.92, 88.42],
  [-15.20, 104.54],
  [-31.57, 120.67],
  [-51.85, 136.79], // 山頂から約98m（採用すると面積が過大になる。既定では使わない）
];

// 川沿い（山頂に近い順）。Dのくさびはこの中から何点採用するかを腱さんが調整する。
const riverPts = [
  [0.68, 57.71],    // 山頂から最短距離(約8m)
  [10.94, 45.49],
  [21.08, 37.43],
  [27.06, 31.44],
  [31.95, 23.26],
  [36.10, 15.19],
  [40.01, 5.05],
  [43.19, -5.08],   // B/C角の近く(約30m)
];

// ABC辺のうちD/Eと接する区間（B/C角→山頂の向き。既にSITES.hirai.subAreaSets.ABCのC区画pts由来、
// bc/tipは上と重複するので除いた「中間点だけ」）
const abcEdgeInterior = [
  [20.25,5.89],[21.7,8.15],[22.11,9.24],[22.41,10.36],[23.39,19.25],[21.83,20.76],[12.71,29.67]
];
```

### E・Dの多角形の組み立て方（`eExtent`・`dExtent`が腱さんの調整パラメータ）

```js
// eExtent: 2〜5（roadPtsを山頂に近い方から何点使うか）。既定2。
// dExtent: 2〜8（riverPtsを山頂に近い方から何点使うか）。既定4。
function buildE(eExtent){ return [tip, ...roadPts.slice(0, eExtent)]; }
function buildD(dExtent){ return [tip, ...riverPts.slice(0, dExtent), bc, ...abcEdgeInterior]; }
```

- 既定値 `eExtent=2` → E面積 **約248㎡**（登記251㎡と±1%で一致）
- 既定値 `dExtent=4` → D面積 **約408㎡**（登記466㎡と-12%。道路と違い川は蛇行が実測しづらく、
  この程度の差は残る前提。だからこそ腱さんが調整するUIが要る）
- 面積は既存の`polygonArea()`（緯度経度から測地計算）または単純な平面シューレース公式のどちらでも良いが、
  **他のA/B/C区画と同じ関数（`trueAreaOfPts`＝`polygonArea(shapeToLatLngs(pts, SITE_XFORM))`）を使うこと**
  （同じ知識を二重に持たない。既存の`priceSimGroups()`等がこの値をそのまま使う）。

## 実装内容

### 1. `SITES.hirai.subAreaSets.DE` を復活させる

`index.html` 959行目付近、現在は空になっている`DE`キー（コメントのみ）を、上記`buildE`/`buildD`の
**現在のeExtent/dExtent設定での実体**で埋める。ただし固定値ではなく、既存の`applyDeSplitPercent()`
（XY案を%から再生成している関数）と同じパターンで、**`eExtent`/`dExtent`が変わるたびに
`SITE.subAreaSets.DE`を再生成する関数**（例：`applyDeExtent()`）を新設し、初期化時とパラメータ変更時に呼ぶ。

`subAreaSets.DE`の要素形式は既存のABC/XYと同じ：`[{no:'D区画 ○○㎡', pts:[...]}, {no:'E区画 ○○㎡', pts:[...]}]`
（`no`の㎡表記は動的に計算した面積を埋め込む。ABC/XYの命名パターンに合わせる）。

### 2. `eExtent`/`dExtent`の永続化・調整UI

`kouzuAdj`と同じ設計（localStorageキー`kouteisa_de_extent_hirai`、`{eExtent, dExtent}`）。
既存の「敷地（区画図トレース）」パネル内、`kouzuToggleWrap`の近くに追加：

```html
<div id="deExtentWrap" style="display:none;margin-top:8px;font-size:12px">
  <div>D/E境界の調整（道路側=E・川側=D。動かすと面積が変わります）</div>
  <div style="display:flex;gap:6px;margin-top:4px">
    <button class="small" onclick="adjustDeExtent('e',-1)">E縮める</button>
    <button class="small" onclick="adjustDeExtent('e',1)">E広げる</button>
    <button class="small" onclick="adjustDeExtent('d',-1)">D縮める</button>
    <button class="small" onclick="adjustDeExtent('d',1)">D広げる</button>
    <button class="small" onclick="resetDeExtent()">既定に戻す</button>
  </div>
  <div class="note" id="deExtentArea" style="margin-top:4px"></div>
</div>
```

`deExtentWrap`は`SITE.subAreaSets && SITE.subAreaSets.DE`を持つ物件（＝平井）だけ表示（`kouzuToggleWrap`の
`has`判定と同じ条件）。`adjustDeExtent(which,delta)`は`eExtent`を2〜5、`dExtent`を2〜8にクランプしてから
`applyDeExtent()`→再描画→`saveDeExtent()`→面積表示更新、を行う（`rotateKouzu`/`scaleKouzu`と同型）。

### 3. 既存の消費側の更新（着手前4問①：同じ知識を持つ場所）

以下は**すでに`SITE.subAreaSets.DE`を見に行く実装が入っている**ため、DEキーさえ正しく埋まれば
自動的に描画・集計されるはず。ただし文言だけ古いので直すこと：

- `deAccuracyHintHTML()`（2288行目付近）: 現在の文言は「公図の手描き線をそのままトレースしたもので
  登記と一致しません」という**3回目の失敗を前提にした説明**。今回は道路・川・敷地境界からの実測トレース
  なので、文言を「道路・川・C区画境界から実測トレース。山側の川の蛇行までは追えないため登記と数%
  ずれます。腱さんが「D/E境界の調整」ボタンで実際の面積に合わせてください」のように更新する。
  ハードコードされている登記値比較（「D 344㎡/登記466㎡」等）は削除し、動的な面積表示に置き換える
  （固定文言に数値を焼き込まない＝正規化の原則）。
- `deSubAreaPolys()`・`drawSubAreaDE()`・`priceSimGroups()`：変更不要のはず（既にDEキー参照のみ）。
  ただし**実装後に必ず動作確認**すること（着手前4問②：前例が成立する前提を今回も確認）。

## 着手前4問（kaishu-policy）の回答

1. **同じ知識を持つ場所**：`deAccuracyHintHTML`・`deSubAreaPolys`・`drawSubAreaDE`・`priceSimGroups`の
   DE分岐・平坦度エリア内訳のDEセクション（2310・2378行目付近）。すべて`SITE.subAreaSets.DE`を単一の
   正本として参照する既存設計なので、新規に複製する場所は無い（`applyDeExtent()`が唯一の書き込み元）。
2. **同種の既存機能**：`kouzuAdj`（画像オーバーレイの手動位置合わせ、localStorage永続化＋ボタンUI）と
   `applyDeSplitPercent()`（XY案をパラメータから動的再生成）。この2つの合成がそのまま今回の設計。
   前提確認：`kouzuAdj`は「画像を動かすだけで下の座標データは変わらない」のに対し、今回は
   「パラメータ変更のたびに`subAreaSets.DE`という座標データ自体を再生成する」点が異なる
   （`applyDeSplitPercent`と同じ前提）。
3. **引っ越しか**：該当なし。
4. **過去の類似改修**：`docs/BUGLOG.md`の3件のD/E失敗エントリ、`~/.claude/skills/kaihatsu-policy/NOTES.md`の
   関連エントリ（画像から形状を読む時は機械抽出を優先し面積合わせの作文をしない、抽出結果は必ず目視で
   ソースに再重畳して確認する）。今回は「画像からの抽出」ではなく「地図タイル上の実座標クリック採取」
   なので機構が異なるが、**「面積を単独の正解として合わせにいかない」**という教訓は今回も適用し、
   登記面積はあくまで参考値・調整の目安として扱い、腱さんの調整UIで最終決定してもらう設計にしてある。
